## 课前引入：页面已经显示了，为什么点击后还可能失败？

我们上一节已经知道：

```text
浏览器
    -> 显示页面

前端
    -> 提供输入框和按钮

后端
    -> 处理数据并生成结果
```

现在观察当前项目的生日占卜页面。页面上有生日输入框、开始占卜按钮和占卜结果区域。

用户填写生日后点击“开始占卜”。页面不会凭空知道结果。它必须把出生时间交给后端，让后端进行处理。

因此，点击按钮之后，背后至少要发生：

```text
前端拿到输入的出生时间
    -> 把它交给后端
    -> 后端收到出生时间
    -> 后端进行处理
    -> 后端把结果交回来
    -> 前端把结果显示出来
```

这里出现了一个新问题：前端和后端不在同一个地方，它们究竟靠什么传递这段数据？

它们通过一种统一的网络沟通规则传递消息，这套规则叫作 HTTP。先不要把 HTTP 想得很复杂，可以把它理解为：浏览器和后端之间约定好的“发消息和回消息的格式”。

## 一、HTTP 到底是什么？

HTTP 的英文全称是 HyperText Transfer Protocol，中文通常叫“超文本传输协议”。现在不用记英文，先理解它做的事情：

```text
前端按照约定发送一条消息
    -> 后端按照约定读取这条消息
    -> 后端按照约定返回另一条消息
    -> 前端读取返回的消息
```

这两条消息分别叫：

```text
Request（请求）
    -> 前端发给后端的消息

Response（响应）
    -> 后端回给前端的消息
```

所以 HTTP 的最基本结构是：

```text
请求
    -> 后端处理
    -> 响应
```

## 二、什么是请求？

请求就是前端向后端提出的一次具体要求。例如：“请根据这个出生时间开始占卜”。

前端不能只发送一句人类语言。它需要按照 HTTP 的格式，把这次请求整理好。一条请求通常包含：

```text
请求方法
请求地址
请求头
请求内容
```

先用餐厅点餐理解这些部分：

| HTTP 请求部分 | 点餐中的对应含义 |
|---|---|
| 请求方法 | 查询菜单，还是提交订单？ |
| 请求地址 | 去哪个窗口？ |
| 请求头 | 我是谁，希望用什么格式交流？ |
| 请求内容 | 具体点什么菜？ |

这只是帮助理解。HTTP 请求的真实组成如下。

### 1. 请求方法：想做什么？

| 方法 | 初步理解 |
|---|---|
| GET | 想获取一些内容 |
| POST | 想提交一些内容，请对方处理 |
| PUT | 想完整替换一份内容 |
| PATCH | 想修改其中一部分 |
| DELETE | 想删除内容 |

当前“提交出生信息，请后端开始占卜”属于 `POST`，因为前端不是单纯读取固定页面，而是在提交数据，请后端处理。

### 2. 请求地址：发给谁？

请求地址告诉前端：这条消息要交给哪个服务的哪个入口？例如：

```text
http://localhost:8000/api/divination
```

```text
http://                 使用的通信规则
localhost               当前这台电脑
8000                    服务所在的端口
/api/divination         后端提供的具体入口
```

`/api/divination` 可以先理解为后端专门接收占卜请求的地址。后面讲 FastAPI 路由时，再详细解释它怎样和某个 Python 函数对应起来。

### 3. 请求头：补充说明

请求头是一些“附加说明”。例如：

```text
Content-Type: application/json
```

它表示：我发送的内容使用 JSON 格式。

```json
{
  "birthday": "2000-08-17 00:00:00",
  "prompt_type": "birthday"
}
```

当前先把 JSON 理解为一种方便前后端共同读取的文字格式。请求头还可能携带登录信息、身份凭证或其他设置。

### 4. 请求内容：真正要提交的数据

请求内容就是这次操作的具体数据。生日占卜可能提交：

```json
{
  "prompt": "2000-08-17 00:00:00",
  "birthday": "2000-08-17 00:00:00",
  "prompt_type": "birthday"
}
```

这部分才是后端真正需要处理的出生时间和占卜类型。

## 三、什么是响应？

响应就是后端处理请求以后，返回给前端的一条消息。后端的响应通常包含处理结果、状态说明、响应头和具体内容。

继续用餐厅例子：请求是“我要点一份菜”；响应是“订单是否接收成功、预计多久、最后端上什么”。

在占卜项目中，响应可能代表：请求是否被接受、出生信息是否符合格式、API 密钥是否配置、占卜结果是什么，以及是否发生错误。

### 1. 状态码：这次请求总体怎样？

后端会给一个数字，叫作状态码。先记住大分类：

| 状态码范围 | 初步含义 |
|---|---|
| 2xx | 请求大体成功 |
| 3xx | 需要转到另一个地址 |
| 4xx | 请求本身有问题 |
| 5xx | 后端处理时出现问题 |

常见例子：

```text
200 -> 后端成功处理
400 -> 前端提交的数据不符合要求
401 -> 需要身份认证
403 -> 后端拒绝这次请求
404 -> 找不到这个地址
500 -> 后端内部发生错误
```

这里要特别注意：`200` 只说明这次 HTTP 沟通成功，不一定代表占卜内容正确。

```text
HTTP 层面成功
    -> 消息成功送达

业务层面成功
    -> 用户真正得到想要的结果
```

### 2. 响应内容：后端到底返回了什么？

响应内容可能是 JSON、HTML、图片、文件或文字。如果是普通接口，可能返回：

```json
{
  "result": "这是占卜结果"
}
```

前端收到后，就能读取 `result` 并显示。当前项目稍后会看到，它的占卜接口不是一次性返回完整文字，而是持续返回一小段一小段的内容，这叫“流式响应”。但这一节只先记住：响应内容就是后端交给前端的数据。流式响应的具体工作方式留到后面的独立章节。

## 四、一个最小的 HTTP 例子

先不看项目，构造一个最简单的场景。前端想提交生日：

```text
请求方法：POST
请求地址：http://localhost:8000/api/divination
请求头：内容是 JSON
```

```json
{
  "birthday": "2000-08-17 00:00:00",
  "prompt_type": "birthday"
}
```

后端处理成功后返回：

```text
状态码：200
```

```json
{
  "result": "占卜结果文本"
}
```

完整过程：

```text
前端准备请求
    -> POST /api/divination
    -> 发送 JSON 数据
    -> 后端收到请求
    -> 后端读取 birthday
    -> 后端处理
    -> 返回 200
    -> 返回 result
    -> 前端显示 result
```

如果后端没有启动：

```text
前端仍然可以显示
    -> 点击按钮
    -> 尝试发送请求
    -> 没有程序接收请求
    -> 请求失败
    -> 页面显示错误或一直等待
```

这就是课前问题的完整解释：页面显示和功能请求成功是两件不同的事。

## 五、把通用概念对应回项目

现在再看项目代码。

### 第一步：页面取得输入

`BirthdayPage.tsx` 保存生日输入。这里先不要深入 React 的 `useState` 或自定义 Hook，只需要理解：页面中保存了用户当前输入的生日。

点击按钮时，页面把输入框中的日期格式转换成后端期待的格式，再调用：

```ts
onSubmit({
  prompt: formattedBirthday,
  birthday: formattedBirthday,
})
```

这一步的核心不是日期算法，而是：

```text
页面中的输入格式
    -> 转换成后端约定的格式
    -> 交给负责发送请求的函数
```

### 第二步：前端准备 HTTP 请求

`useDivination.ts` 中：

```ts
const headers: Record<string, string> = {
  Authorization: `Bearer ${jwt || 'xxx'}`,
  'Content-Type': 'application/json',
}

await fetchEventSource(`${API_BASE}/api/divination`, {
  method: 'POST',
  body: JSON.stringify({ ...params, prompt_type: promptType }),
  headers,
})
```

先不展开 `fetchEventSource` 的流式机制，只观察它传入了什么：

```text
请求地址：${API_BASE}/api/divination
请求方法：POST
请求内容：JSON.stringify(...)
请求头：headers
```

`JSON.stringify` 做的事情是：

```text
JavaScript 对象
    -> 转换成 JSON 文字
    -> 放进 HTTP 请求内容
```

### 第三步：后端登记接收入口

后端 `chatgpt_router.py` 中有：

```python
@router.post("/api/divination")
async def divination(request: Request, divination_body: DivinationBody):
    ...
```

现在把它和前端的请求对应起来：

```text
前端：POST /api/divination
后端：@router.post("/api/divination")
```

这表示：前端向 `/api/divination` 发送 POST 请求时，后端调用 `divination()` 函数。

### 第四步：后端按照约定读取请求内容

`models.py` 定义了：

```python
class DivinationBody(BaseModel):
    prompt: str
    prompt_type: str
    birthday: Optional[str] = None
```

它表达后端期待的数据结构：

```text
prompt       必须是文字
prompt_type  必须是文字
birthday     可以有，也可以没有
```

前端发来的 JSON 会被框架整理后交给 `DivinationBody` 进行检查。这里的通用知识是：前后端必须提前约定数据长什么样，否则后端不知道怎样读取前端发出的内容。

这个约定包括字段叫什么、是否必须存在、是什么类型、允许什么格式。

## 六、当前完整数据链

```text
用户填写出生时间
    -> 前端保存输入
    -> 前端整理日期格式
    -> 前端创建 POST 请求
    -> 请求地址是 /api/divination
    -> 请求内容是 JSON
    -> 后端找到 divination()
    -> 后端把 JSON 整理成 DivinationBody
    -> 后端继续处理
    -> 返回响应
    -> 前端读取响应
    -> 页面显示占卜结果
```

这里已经能把项目中的代码转换成 HTTP 知识：

```text
请求方法       -> POST
请求地址       -> /api/divination
请求头         -> Content-Type、Authorization
请求内容       -> JSON.stringify(...)
后端数据模型   -> DivinationBody
后端处理函数   -> divination()
响应           -> 后端返回给前端的结果
```

本节学会：

```text
Request 是前端发给后端的消息
Response 是后端返回给前端的消息

响应包含状态码和返回内容

页面能显示，不代表后端请求一定成功
```

# 【Python 运行】模块导入与 `server:app` 的应用对象发现

下面这节展示另一种同样必须模仿的成品形状：主题不是 HTTP，而是启动器如何从 `模块名:对象名` 找到应用。它保留相同的教学完成度，但概念、最小例子、代码证据和边界全部围绕一个新知识系统展开。

今天只学服务如何“找到并启动”这个项目的 Web 应用，不讲路由匹配、数据库初始化细节或浏览器渲染。

## 本节速览

```text
启动命令
    -> Python 导入模块
    -> 执行模块顶层代码
    -> 创建 app 对象
    -> Uvicorn 按名字取得 app
    -> Uvicorn 开始监听并转交请求
```

## 课前现象

运行项目的启动命令后，终端显示本地地址；打开地址，服务就能回应。

但命令里的 `server:app` 只是文字。它怎样变成一个正在工作的 Web 应用？

答案是：`server` 指定 Python 模块，`app` 指定该模块里已经创建好的对象。

## 通用过程

启动器读到 `server:app`。

```text
启动器读到 server:app
    -> 让 Python 导入 server 模块，也就是加载并执行 server.py
    -> Python 从上到下执行文件顶层代码
    -> import 依赖、创建应用对象、登记配置
    -> 执行到 app = FastAPI(...) 时，内存里出现名为 app 的应用对象
    -> 启动器从 server 模块中取出 app
    -> 启动器持续监听端口，并把请求交给 app 处理
```

这里的关键分工是：

```text
Python
    -> 导入和执行模块，创建对象

Uvicorn
    -> 网络服务器，监听端口并把 HTTP 请求交给应用对象

app
    -> 应用入口；之后才负责路由、响应等 Web 行为
```

## 最小例子

```python
# demo.py
app = {"name": "my app"}
```

若某个启动器接收 `demo:app`：

```text
demo
    -> 导入 demo.py

app
    -> 取出其中的 app 变量

得到
    -> {"name": "my app"} 这个对象
```

Web 项目中，对象不再是字典，而是能处理请求的 FastAPI 应用对象，但“模块名:对象名”的发现机制相同。

## 回到 `suan` 项目

在 `start.sh` 的最后一行：

```bash
exec python3 -m uvicorn server:app --host 127.0.0.1 --port "$PORT"
```

这表示：

```text
python3 -m uvicorn
    -> 以 Python 模块方式启动 Uvicorn

server:app
    -> 导入 server.py，取得其中的 app

--host 与 --port
    -> 让 Uvicorn 在指定本地网络地址等待请求
```

而在 `server.py`：

```python
app = FastAPI(title="...", version="2.0")
```

这正是 `server:app` 最终要找到的对象。

随后，模块顶层代码继续给该对象添加 CORS 中间件、注册 API 路由、挂载静态资源。它们不是启动器“自动发现”的；而是在导入 `server.py` 时执行代码，逐步配置到同一个 `app` 对象上的。

## 一条重要边界

正常情况：`server.py` 能导入、依赖存在、文件中有 `app`，Uvicorn 就能启动。

常见失败：

```text
server 写错或文件不在当前模块搜索路径中
    -> 找不到模块

app 写错或未创建
    -> 找不到属性

server.py 顶层 import 某个依赖失败
    -> 应用对象尚未创建，启动直接失败
```

`@app.on_event("startup")` 中的数据库初始化属于“应用已经被发现后，开始接受请求前的生命周期步骤”；下一节再单独讲它。

## 当前任务锚点

```text
目标
    -> 能解释 server:app 如何从命令文本变成实际应用对象

已验证证据
    -> 启动脚本确实传入 server:app
    -> server.py 确实在顶层创建 app

下一步
    -> 学习 Uvicorn 得到 app 后，如何把 HTTP 请求转交给 FastAPI 路由
```
